# 状态采样与发布解耦设计

## 1. 背景与问题

`SystemStatusStore` 当前把电池、网络、系统健康和电源策略放在同一轮刷新中读取。虽然读取任务并发启动，快照仍必须按固定顺序等待全部 Provider 完成后才发布，因此网络或 helper 的慢查询会拖住已经完成的电池和 CPU 状态。任意 Provider 事件也会触发四个 Provider 全量读取。

弹出面板和电源页还会在出现时主动调用全量刷新，电源页会在电源来源变化时再次刷新。这些调用可能与页面转场或后台采样重叠，并增加无关状态的刷新和视图更新。

## 2. 目标

- 电池、系统健康不再等待网络或电源策略读取即可发布最新值。
- 网络事件只读取网络 Provider；电源策略事件只读取电源策略 Provider；其他事件保持对应域隔离。
- 网络和电源策略保留事件驱动，并增加 30 秒低频兜底读取。
- 后台采样和快照发布分离：每个状态域读取完成后更新缓存并重建统一快照。
- 电源页不再在出现或电源来源变化时主动触发刷新；它只消费状态源提供的电池/电源状态。
- 电源控制写入后的读回只等待电源策略域，不重新读取无关 Provider。
- 保持 `SystemStatusSnapshot` 作为现有 UI 和控制层的统一兼容入口。

## 3. 非目标

- 不改变 BatteryProvider、NetworkProvider、HealthProvider 或 PowerPolicyProvider 的平台读取逻辑。
- 不改变网络、电源策略或控制能力模型的业务语义。
- 不引入新的页面状态存储层或更换 SwiftUI 的观察机制；本次以刷新域隔离和移除页面主动刷新为范围。
- 不修改用户当前已有的未提交文件。

## 4. 设计方案

### 4.1 状态域与调度

`SystemStatusStore` 继续持有四个状态缓存和一个 `@Published` 的 `snapshot`，但刷新入口按 Provider 划分：

| 状态域 | 触发方式 | 发布行为 |
| --- | --- | --- |
| 电池 | 启动、唤醒、现有电池事件、高频采样 | 读取完成后立即更新电池缓存并发布快照 |
| 健康 | 启动、唤醒、热状态/低电量模式相关事件、高频采样 | 读取完成后立即更新健康缓存并发布快照 |
| 网络 | 启动、唤醒、网络事件、30 秒兜底 | 读取完成后立即更新网络缓存并发布快照 |
| 电源策略 | 启动、唤醒、电源状态事件、30 秒兜底、控制读回 | 读取完成后立即更新电源缓存并发布快照 |

高频采样任务只负责请求电池和健康域，间隔沿用现有 `samplingIntervalNanoseconds`（默认 1 秒）。低频任务只负责请求网络和电源策略域，默认间隔为 30 秒，并通过初始化参数注入以便测试。

启动和唤醒会分别请求四个域的首读，但这些读取彼此独立；任何一个慢查询都不会阻止其他域发布。事件回调不再共享一个全量刷新闭包，而是绑定到对应的域刷新请求。

### 4.2 并发与刷新合并

每个状态域维护自己的 in-flight 标记或任务。相同域已有读取时，新的事件或采样请求不会再启动第二个并发读取；读取结束后缓存只由主 Actor 更新，并重建 `SystemStatusSnapshot`。

刷新请求必须支持停止和睡眠生命周期：停止时取消调度任务并解除 Provider 观察；已返回的读取结果在 Store 已停止后不得重新启动新的调度。唤醒时重新启动高频和低频任务，并重新请求四个域的首读。

`refreshNow()` 如保留为 Store 的内部兼容入口，只负责并行提交四个域的独立刷新请求，不再等待或串联 Provider。新增电源域等待入口，供控制层在写入、授权或注销 helper 后等待电源策略读回。

### 4.3 快照发布

每个域读取成功或返回不可用状态后，写入对应缓存并调用统一的快照重建函数。重建函数继续使用最新的四个缓存值，更新时间表示本次域更新的提交时间；未参与本次读取的其他域保持其最近一次值。

这样可以保留现有 `snapshot` API，同时允许电池/CPU 先于网络/helper 发布。Provider 的不可用结果仍只影响对应域，不会用全量刷新结果覆盖其他域。

### 4.4 页面与控制层

- `StatusPopoverView` 删除打开面板时的主动刷新；Store 从应用启动开始持续采样并接收事件。
- `PowerControlView` 删除 `onAppear` 和电源来源 `onChange` 中的主动刷新。电源来源变化由 BatteryProvider 事件更新电池状态；电源策略变化由 PowerPolicyProvider 事件或 30 秒兜底更新。
- `ControlCoordinator` 将写入、授权和注销 helper 后的 `refreshNowAndWait()` 改为电源域专用等待入口，读回校验仍基于最新的电源策略状态。
- 页面继续从统一 Store 读取所需的电池和电源策略字段，不再承担刷新调度职责。

## 5. 错误处理与边界

- Provider 返回 `.unavailable` 或其他降级状态时，立即发布该域的结果；其他域保留最近值。
- Provider 读取任务的失败路径必须转换为该 Provider 已有的不可用模型，不能因为单域失败取消其他域的采样任务。
- 读取任务不能因网络或 helper 阻塞高频采样任务。
- 重复事件在同一域已有读取期间合并，避免事件风暴产生并发 helper、CoreWLAN 或系统 API 查询。
- 全量兼容入口不再作为 UI 生命周期钩子使用；只允许生命周期恢复或明确的协调层场景调用。

## 6. 验证计划

增加或调整状态源测试，覆盖：

1. 慢网络/电源 Provider 未完成时，电池和健康结果已经发布。
2. 网络事件只增加网络 Provider 的读取次数，电源事件只增加电源策略 Provider 的读取次数。
3. 高频采样不会按采样间隔重复读取网络和电源；低频间隔可注入为短值验证 30 秒兜底逻辑。
4. 同一 Provider 的重叠请求会合并，停止后不会继续发布后台调度结果。
5. 控制层等待电源策略域后可以完成读回校验，不触发电池、网络或健康读取。
6. 现有统一快照和 Provider 失败隔离测试继续通过。

静态检查确认 `StatusPopoverView` 和 `PowerControlView` 不再调用主动刷新入口；最后运行 Xcode 单元测试，并检查工作区 diff 只包含本次状态刷新改动与设计文档，不覆盖用户已有改动。
